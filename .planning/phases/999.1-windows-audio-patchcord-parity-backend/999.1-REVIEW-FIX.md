## Fixed Issues

### WR-01: App INCLUDE mode passes `undefined` PID to the native addon when no app is selected

**Files modified:** `src/modules/native/wasapiLoopback.ts`
**Commit:** `614ea6e`
**Applied fix:** Added an explicit PID guard at the top of the `mode === "app"` dispatch branch in
`tryStartWasapiLoopback`. Before calling `wasapi.startIncludeProcessTree(...)`, it now reads
`const targetPid = audioConfig.pids[0]` and, if `targetPid` is not a positive integer
(`typeof !== "number" || !Number.isInteger || <= 0` — i.e. the user chose app mode but checked no
app, so `pids` is `[]`), it tears down the just-created port via `stopWasapiLoopback()`, writes an
`app-no-pid` line to `wasapi-capture.log` (consistent with the existing `logCapture` diagnostics),
and returns `closedVerdict` (which is `failed-no-fallback` for app mode). This removes the prior
dependence on napi's argument validation throwing (caught by the outer `try/catch`) and eliminates
the risk of a coercion to PID 0 (System Idle) rooting the INCLUDE tree. The native start is now
only reached with a validated `targetPid`. Fails closed deterministically; strengthens invariant (a).

**Verification performed:**
- Tier 1: re-read the modified block — guard present, surrounding dispatch intact.
- Tier 2 (lint): `oxlint src/modules/native/wasapiLoopback.ts` → 0 warnings / 0 errors.
- Note on `bun run check`: this file carries a top-level `// @ts-nocheck` (Bun cannot install the
  wasapi-loopback addon off-Windows, mirroring `venbind.ts`), so tsgo type-checking is a deliberate
  no-op for this file by design — lint + re-read are the meaningful static gates here. The isolated
  worktree also has no `node_modules` (CI-only build policy); lint was run using the main tree's

## Skipped Issues

### WR-02: `stop()` detach window can double-run WASAPI capture across a re-click

**File:** `native/wasapi-loopback/src/lib.rs:799-836` (`stop`) — plus the byte-identical mirror
`wasapi-loopback-repo/src/lib.rs`
**Status:** SKIPPED (deliberate — needs a box-verified fix, not a blind auto-fix)
**Original issue:** `stop()` clears `SESSION` immediately (`guard.take()`), signals the stop event,
then joins with a bounded 1500 ms timeout. On timeout it detaches the still-running capture thread
and `CloseHandle`s the stop event. Because `SESSION` is already `None`, an immediately-following
`start*` (the "cancel and start again" re-click, now reachable in 3 more variants) can spin up a
SECOND capture client while the detached thread is still inside `run_capture_loop` — two concurrent
WASAPI loopback captures = the CoreMessaging co-run hard-crash condition. Secondary: the detached
thread keeps polling `WaitForSingleObject(stop_event, 0)` after `stop()` has `CloseHandle`d that
handle (wait on a closed/possibly-reused handle).

**Reason for skipping:** A correct fix is non-trivial concurrency/lifecycle rework, not a minimal
obviously-correct change:
- Closing the co-run window requires a NEW global "teardown-in-progress" atomic flag, set before
  the thread is detached and cleared by the capture thread on its way out, and checked by ALL start
  entry points (`start`, `start_include_process_tree`, `start_endpoint_session`) so a fresh client
  refuses (`Ok(false)`) while a prior detached thread is still alive.
- Fixing the wait-on-closed-handle race requires transferring `stop_event` HANDLE ownership from
  `stop()` to the capture thread (thread closes its own handle on exit), which also changes the
  `CloseHandle` discipline in the three `!supported` early-teardown paths that currently close it.
- This is coordinated change across 4+ sites in TWO byte-identical mirror files.

This code is SHIPPED as PR #211 and governs the fork's CORE VALUE ("start a screenshare, cancel,
start again — and it works, without getting stuck"). A wrong change here regresses restart-after-
cancel or hangs `stop()`. Per project constraints it CANNOT be compiled locally (CI-only Rust
build) and CANNOT be verified without a Windows box exercising the cancel→restart path — so it is
not "obviously-correct-by-construction from reading alone." Forcing an unverifiable concurrency
change into shipped core code is exactly what must not be auto-applied. This finding needs a
deliberate, CI-compiled, box-verified fix (and, per IN-02, is best done alongside the single-helper
extraction so the fix lives in one place across both mirrors — that refactor is Info-scope and also
out of this fix pass).

**Recommended next step:** hand WR-02 to a dedicated, box-verified Rust change: add the
teardown-in-progress guard + handle-ownership transfer, apply identically to both mirrors
(`diff -q` clean), then compile via GitHub CI and re-verify the picker/cancel/re-click flow on the
Windows box before considering it resolved.
