**Gathered:** 2026-07-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Grow the Windows WASAPI process-loopback addon from a fixed echo-fix (shipped #211: EXCLUDE-of-own-process-tree) into a patchcord-parity audio backend by shipping **exactly two new capture features**:

1. **Per-app INCLUDE (single app)** — Discord-style app-exclusive share via `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`. Self-free / VAC-free / delay-free / AEC-free **by construction** (native engine-side filter). This is the patchcord-parity headline the maintainer asked for on PR #211 ("same API as patchcord, include/exclude any apps, not just prevent echo").
2. **Endpoint/source selector** — user picks which render device GoofCord captures (endpoint loopback of the chosen `IMMDevice`). The VAC/virtual-cable fix: a Sonar/VoiceMeeter user points GoofCord at their clean stream bus (e.g. `SteelSeries Sonar - Stream`) → echo-free, native quality, no driver, no AEC. Same model OBS uses.

**Unchanged / not in scope to alter:** EXCLUDE-self stays the **zero-config default** for `mode:"system"` (shipped #211). Non-VAC users need no new config.

**Explicitly OUT of this deliverable** (see Deferred): AEC/subtraction of any kind, GoofCord-shipped virtual audio driver, B1 deterministic multi-capture subtraction, multi-app N-INCLUDE + mixer, dedicated window capture, restart-follow (patchcord `createMatcher` analog).

The phase may ship as one plan or two (INCLUDE first, selector second); ship order between them is flexible. Per-app INCLUDE is the recommended first ship (smallest PR-able win + the parity headline).
</domain>

<decisions>
## Implementation Decisions

### Locked — do NOT re-litigate (settled across research milestone + 3 on-box AEC spikes)
- **NO AEC / no subtractive self-cancellation.** Any subtractive canceller needs to *estimate* the echo path → convergence/calibration ramp + alignment/buffering latency. "No delay, no calibration" is a hard requirement. On-box proof: calibration reset on every speech gap (`reason=reference_inactive`), voice is bursty → never converged. The entire subtractive family (NLMS, WebRTC AEC3, Windows CWMAudioAEC) is dead. Do not reopen.
- **GoofCord will NOT ship a virtual audio device / driver.** Against maintainer philosophy (portable/clean, no bundled driver). OBS model: users who need it bring their own VAC (VB-Cable / VoiceMeeter / SteelSeries Sonar).
- **Patchcord-quality = routing + include/exclude apps**, delivered by the two features above — NOT by subtraction. patchcord itself routes; it never subtracts.
- **`mode:"system"` keeps EXCLUDE-self as the zero-config default** (shipped #211). This deliverable adds new *opt-in* modes around it; it does not change the default behavior.
- **App mode AND explicit-endpoint mode MUST fail closed.** On activation failure → no audio. NEVER fall back to Chromium `"loopback"` (privacy inversion: user asked for one app / one device, silent fallback captures everything; plus the CoreMessaging hard-crash landmine).
- **Single-app INCLUDE only (N=1) ships and is verified.** Multi-app N-INCLUDE is NOT in Discord's native behavior and is UNTESTED (R4 concurrency spike unrun). Keep the addon API **`pids[]`-shaped from day one** so multi-app can be added later with no ABI break, but ship/verify N=1.
- **Enumerate audio sources by audio session, not by window.** `IAudioSessionManager2` → `IAudioSessionControl2::GetProcessId` (we want audio apps and already have a checklist UI). Diverges from OBS's window picker deliberately.
- **Never run Chromium `"loopback"` concurrently with any native WASAPI capture** (CoreMessaging hard-crash). If any native capture starts, leave `result.audio` unset. Already avoided at `screenshare.ts:101-110`; preserve it.
- **Format is hardcoded 48000 Hz / stereo / f32 / 480-frame / 3840-byte** for every native path (process-loopback device returns `E_NOTIMPL` from `GetMixFormat`). The endpoint-loopback path uses the SAME fixed format via `AUTOCONVERTPCM` + `SRC_DEFAULT_QUALITY` — NOT `GetMixFormat`. The transport feeder (`wasapiTransport.ts`) is format-agnostic; do not change it.
- **OS floor stays dynamic.** Keep the addon's dynamic `ActivateAudioInterfaceAsync` entrypoint probe + try-activate-and-catch. NO hard build-number gate (docs conflict 19041 vs 20348). When unsupported → return `false` and hide/disable app + endpoint modes; never silently fall back.
- **One `TargetProcessId` + one mode per activation.** No multi-target, no include+exclude in one client. Multi-EXCLUDE ("system minus self minus app X") is not expressible in `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS`; INCLUDE is the path.
- **B1 deterministic subtraction is PARKED (not in this deliverable).** It only helps a narrow config (GoofCord rendering *directly* to a physical endpoint with a VAC bus also on it — the user won't route this way); provably dead for B2 (GoofCord laundered *through* a VAC process, incl. the reference user's Sonar setup); degrades under APOs/limiter; rests on 3 unverified on-box assumptions. Even if a future viability test passes, keep it OUT of the patchcord-parity PR (novel DSP).

### Config model (persisted `AudioConfig`)
```ts
interface AudioConfig {
  mode: "none" | "system" | "app";
  pids: number[];                                // app mode: chosen app PID(s) — single for now, array-shaped for later multi
  captureSource: "process-exclude" | "endpoint"; // system-mode backend selector
  endpointId: "default" | string;                // endpoint mode: chosen IMMDevice id ("default" sentinel)
}
```
- `mode:"none"` → no audio.
- `mode:"system"`, `captureSource:"process-exclude"` → EXCLUDE-self (default, today's behavior).
- `mode:"system"`, `captureSource:"endpoint"`, `endpointId` → endpoint loopback of the chosen render device (the selector / VAC fix).
- `mode:"app"`, `pids` → INCLUDE the chosen app's process tree.
- Normalize older saved configs in preload (fill missing `captureSource`/`endpointId`).

### Claude's Discretion (decide during planning/implementation, within the locked constraints above)
- Exact Rust addon function signatures/names for the new INCLUDE + endpoint + enumerator exports (the handoff proposes `startIncludeProcessTree`, `listAudioApps`, `listRenderEndpoints`, `startRenderEndpoint`/`startDefaultRenderEndpoint` — refine as needed; keep `start`/`stop` as the compat EXCLUDE path).
- The richer verdict shape returned by `tryStartWasapiLoopback` (`started` / `unsupported-fallback-ok` / `failed-no-fallback` or equivalent) — as long as app + explicit-endpoint modes fail closed.
- Exact userData log format/location for capture-kind diagnostics (no DevTools on the test box).
- Selector UI presentation (dropdown of "Default" + render endpoints for `mode:"system"`) within the existing picker.
- Whether to split into one phase-plan or two; recommended INCLUDE first, selector second.
</decisions>

<specifics>
## Specific Ideas

### What already exists (de-risks the work — reuse verbatim, do NOT rebuild)
- `AudioConfig` type + renderer→handler IPC flow (`preload.mts:14-16`); Linux consumes it, Windows currently throws it away.
- Picker UI already built: `audioMode` segmented control + `#audio-apps-list` checklist. Lights up automatically once `audioNodes` is populated on win32.
- Addon clean-room patterns reusable verbatim: dynamic `ActivateAudioInterfaceAsync` probe, `ManuallyDrop<PROPVARIANT>` guard, on-capture-thread activation w/ channel verdict, event-driven drain, copy-before-`ReleaseBuffer`, zero-fill on `AUDCLNT_BUFFERFLAGS_SILENT`, idempotent `stop()` from any state, 64-bit counters (49-day wrap).
- Transport unchanged: `ChunkTsfn` → `MessageChannelMain` → `wasapiTransport.ts` MSTG feeder (fixed 48000 Hz / stereo / f32 / 480-frame / 3840-byte).
- Proven on-box (AEC spike lineage): process-loopback INCLUDE rooted at the Electron **main** `process.pid` DOES capture the audio-service child's render → INCLUDE of a target app's tree will capture its audio. Concurrent endpoint-loopback + one process-loopback INCLUDE is stable in Electron (no CoreMessaging crash).

### Enumerator detail (for `listAudioApps`)
Enumerate all active `eRender` endpoints → `IAudioSessionManager2::GetSessionEnumerator` → `IAudioSessionControl2::GetProcessId`; dedupe by PID; drop `IsSystemSoundsSession` + GoofCord's own tree; name via session `GetDisplayName` else `QueryFullProcessImageNameW` basename. Shape ≈ `{ processId, displayName, binary }` — exactly what the existing picker needs. Do NOT widen the renderer contract.

### Endpoint enumerator/loopback detail
`EnumAudioEndpoints(eRender, DEVICE_STATE_ACTIVE)`, `GetId` + `PKEY_Device_FriendlyName`, tag default. `"default"` sentinel → `GetDefaultAudioEndpoint(eRender, eConsole)`. Endpoint loopback = `Activate(IAudioClient)` on the `IMMDevice`, `Initialize` with `LOOPBACK | EVENTCALLBACK | AUTOCONVERTPCM | SRC_DEFAULT_QUALITY` at the fixed 48k/stereo/f32 format.

### Verification ledger (CI = const/compile; BOX = Windows runtime — manual, no automated repro)
- CI: binding constants vs SDK headers (`VAD\Process_Loopback`, IIDs, `VT_BLOB`, `PKEY_Device_FriendlyName` GUID/PID 14, HRESULTs); windows-rs feature gates for `IAudioSessionManager2` / `IMMDeviceEnumerator` / property store.
- BOX: INCLUDE of a real 3rd-party app tree delivers 48k/f32 via `AUTOCONVERTPCM`; silence when quiet.
- BOX: session enumeration correctness from the addon MTA thread; `AUDCLNT_S_NO_SINGLE_PROCESS` frequency; name/icon fallback quality; Discord's own session PID (main vs audio-service child).
- BOX: endpoint loopback at the fixed format on real devices; `"default"` → `GetDefaultAudioEndpoint(eRender, eConsole)`.
- BOX (**Sonar-specific open question**): is `SteelSeries Sonar - Stream` exposed as a **render endpoint** (loopback-capture) or a **capture/input device** (direct capture)? The selector must handle whichever — verify and support both if needed.
- BOX: app mode + explicit-endpoint mode fail **closed** (no audio) on activation failure, never Chromium fallback.
- BOX: OS-floor matrix 19041/19045/20348/22000+ — activate or degrade to `false` cleanly.

<deferred>
## Deferred Ideas (NOT in this deliverable)

- **B1 deterministic subtraction** — parked. Cheap gating test BEFORE any build: on-box, (a) is the endpoint gain queryable (`ISimpleAudioVolume` × `IAudioEndpointVolume`, `QueryHardwareSupport`)? (b) is the endpoint↔process-loopback sample offset stationary (<1 sample / 30 min via QPC/device-position)? If either fails, B1 is dead. Even if both pass, keep it OUT of the patchcord-parity PR.
- **Multi-app N-INCLUDE + mixer** — deferred; not in Discord's native behavior; UNTESTED. Requires the R4 concurrency spike first (2–3 concurrent INCLUDE clients + mixer stable in Electron, repeated start/stop). Keep the addon API `pids[]`-shaped so it slots in later.
- **Restart-follow** (patchcord `createMatcher` analog) — nice-to-have; process-loopback binds a raw PID, so a restarted app isn't followed. Not required for the first ship.
- **Dedicated window capture** (à la OBS window capture) — deferred.
- **endpoint-self-cancel / AEC config variants** — dead; drop from any config surface.
</deferred>
