## Summary

Reviewed the per-app INCLUDE / render-endpoint / config-dispatch additions layered on the
shipped #211 WASAPI EXCLUDE-tree code. The new diff spans the Rust addon (INCLUDE mode,
endpoint loopback, `listAudioApps`/`listRenderEndpoints` enumerators), the TS wrapper's
`WasapiVerdict` dispatch, the screenshare gate, the preload picker UI, and the schema default.

**The two HARD safety invariants hold and were verified:**

- **Fail-closed (T-999.1-04/05/10/12):** In `wasapiLoopback.ts` `closedVerdict` is
  `unsupported-fallback-ok` ONLY when `mode==="system" && captureSource==="process-exclude"`;
  every app / endpoint path resolves to `failed-no-fallback`. In `screenshare.ts` the ONLY
  branch that sets `result.audio = "loopback"` is `verdict === "unsupported-fallback-ok"`.
  There is **no path** where an app- or endpoint-mode native failure sets `result.audio`.
  The privacy-inversion / CoreMessaging co-run fallback is correctly unreachable for the
  strict modes. No Critical finding here.
- **Fixed transport format:** Both new client-acquisition paths (`activate_process_tree`
  INCLUDE and `activate_render_endpoint_loopback`) route through the shared
  `initialize_loopback_client` (hardcoded 48k/stereo/f32 + `AUTOCONVERTPCM`); neither calls
  `GetMixFormat`. Chunk shape stays 3840 bytes via the shared `run_capture_loop`.

FFI-safety spot checks passed: the new `PROPVARIANT` from `IPropertyStore::GetValue` is left
to drop (owning, `PropVariantClear`) while `GetDisplayName`/`GetId` `PWSTR`s are `CoTaskMemFree`d
(non-owning) — correct and distinct discipline, no double-free. Enumerators are fail-closed on
a joined worker thread (`unwrap_or_default()`), so a panic collapses to `[]` without crossing
FFI. Renderer HTML sinks (`renderAudioApps` display name, endpoint `<option>` id/label) are
`escapeHtml`-guarded, so hostile audio-session / device names cannot XSS the picker. Cargo
feature gates for the two new type families (`Win32_UI_Shell_PropertiesSystem` for
`IPropertyStore`, `Win32_Devices_FunctionDiscovery` for `PKEY_Device_FriendlyName`) are present.

**Note on the mirror:** `native/wasapi-loopback/src/lib.rs` and the byte-identical
`wasapi-loopback-repo/src/lib.rs` were confirmed `diff -q` clean. Every Rust finding below
applies to BOTH copies and must be fixed in both.

## Warnings

### WR-01: App INCLUDE mode passes `undefined` PID to the native addon when no app is selected

**File:** `src/modules/native/wasapiLoopback.ts:279` (also `src/windows/screenshare/preload/preload.mts:141` — where `pids` is built with no min-selection check)
**Issue:** In app mode the dispatch calls `wasapi.startIncludeProcessTree(audioConfig.pids[0], onChunk)` with no guard that `pids` is non-empty. If the user picks "app" mode but checks no app in the checklist, `getFormSettings` produces `pids: []`, so `pids[0]` is `undefined`. That `undefined` is handed to a napi `u32` parameter. napi-rs rejects it (number expected), the throw is caught by the outer `try/catch`, and the function returns `closedVerdict` = `failed-no-fallback` → a silent, audio-less share with **no user-visible feedback** that their selection was ignored. Behaviour also depends on napi's argument-validation throwing rather than coercing to `0` (INCLUDE tree rooted at PID 0 = System Idle, unspecified capture) — an implementation detail this code should not rely on. Fails closed (safe), but the silent-no-audio outcome is a real defect.
**Fix:** Guard explicitly before the native call, e.g.:
```ts
} else if (audioConfig.mode === "app") {
    const targetPid = audioConfig.pids[0];
    if (!targetPid || !Number.isInteger(targetPid) || targetPid <= 0) {
        await stopWasapiLoopback();
        await logCapture("app-no-pid", closedVerdict);
        return closedVerdict; // fail closed, but deterministically (not via a napi throw)
    }
    kind = "include-pid";
    ok = await wasapi.startIncludeProcessTree(targetPid, onChunk);
}
```
Additionally consider blocking the "Start" button in the preload when app mode is chosen with zero apps checked, so the user gets feedback instead of a silent silent-audio share.

### WR-02: `stop()` detach window can double-run WASAPI capture across a re-click (shared/pre-existing code, aggravated by the new modes)

**File:** `native/wasapi-loopback/src/lib.rs:799-836` (`stop`, shared by every capture mode; both mirror copies)
**Issue:** `stop()` does `guard.take()` (clears `SESSION` immediately), signals the stop event, then joins with a bounded 1500 ms timeout. On timeout it **detaches** a still-running capture thread and `CloseHandle`s the stop event. Because `SESSION` is already `None`, an immediately-following `start*` call (the core "cancel and start again" re-click flow, now reachable in 3 more variants: INCLUDE, endpoint, default-endpoint) will spin up a SECOND capture client while the detached thread is still inside `run_capture_loop` holding the OLD `IAudioClient` and pushing to the OLD ThreadsafeFunction. Two concurrent WASAPI loopback captures in the same session is exactly the co-run condition the design flags as a CoreMessaging hard-crash risk. Secondary: the detached thread keeps polling `WaitForSingleObject(session.stop_event, 0)` after `CloseHandle(session.stop_event)` — a wait on a closed (potentially reused) handle. The window is narrow (only when native teardown exceeds 1500 ms) and the root logic predates this phase, but the new multi-mode dispatch widens the surface and it bears directly on the co-run safety invariant.
**Fix:** Have `run_capture_loop` own its per-loop copy of the stop `HANDLE` lifetime, and prefer a definite join on the fast path; on detach, do NOT `CloseHandle` the stop event from `stop()` — transfer ownership to the thread so it closes its own handle on exit (avoids the wait-on-closed-handle race). To close the co-run window, gate `start*` so it refuses (returns `Ok(false)`) while a previous detached thread is still alive — e.g. a global "teardown in progress" flag cleared by the capture thread on its way out — rather than allowing a fresh client to activate over a still-live one.

## Info

### IN-01: `wasapi-capture.log` grows unbounded

**File:** `src/modules/native/wasapiLoopback.ts:185-192`
**Issue:** `logCapture` appends one line per share attempt to `userData/wasapi-capture.log` with no rotation or truncation. Over a long-lived install this file grows without limit. It is a deliberate no-DevTools diagnostic and low-risk, but unbounded.
**Fix:** Cap the file (truncate when it exceeds e.g. 256 KB, or keep only the last N lines), or gate the write behind a debug flag once Windows verification is complete.

### IN-02: ~40 lines of session-start boilerplate duplicated across four napi entry points

**File:** `native/wasapi-loopback/src/lib.rs:557-623` (`start`), `639-703` (`start_include_process_tree`), `711-773` (`start_endpoint_session`) — both mirror copies
**Issue:** `start`, `start_include_process_tree`, and `start_endpoint_session` are near-identical: same `SESSION` idempotency guard, stop-event creation, channel-verdict handshake, thread spawn, `run_capture_loop` reuse, and teardown — differing only in the single `activate_*` call. The code documents this as intentional, but the duplication means a future fix to the handshake/teardown (see WR-02) must be applied in three places per file across two files (six sites total), which is error-prone.
**Fix:** Extract the shared body into one private helper taking a closure/enum that selects the activation (e.g. `run_session(activate: impl FnOnce() -> ActivationResult, on_chunk)`), leaving each `#[napi]` export a one-line wrapper. This also localizes the WR-02 fix to a single place.
