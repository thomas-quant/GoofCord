# NEXT — Multi-app N-INCLUDE mixing (chosen 2026-07-04)

**Decision (user):** Build **real multi-app N-INCLUDE** — checking several apps in the picker should mix ALL of them to the viewer, not just the first. Chosen after on-box testing of the 999.1 build.

## Why this is now a thing
- The picker (`#audio-apps-list`) is a **multi-select checklist** (inherited from the Linux/patchcord path), so it *invites* checking multiple apps.
- The backend is **single-app**: `wasapiLoopback.ts:285` uses `audioConfig.pids[0]` → `startIncludeProcessTree(pid)`, and the Rust addon has ONE capture `SESSION`. Checking N apps captures only the first (`pids[0]`).
- On-box log confirmed single-app works (`include-pid started`) and WR-01 fail-closed works (`app-no-pid → failed-no-fallback`). The gap is purely the N-app mixing, which was deferred at design time.

## What it takes (scoped, for a future phase/plan)
- **Rust addon (both byte-identical mirrors):** run **N concurrent process-loopback INCLUDE clients** (one per PID) + a **mixer** that sums their PCM into the single fixed 48k/stereo/f32 / 3840-byte output. Today's single `SESSION` becomes N sessions feeding one mixer → one `ChunkTsfn`.
  - Feasibility is established: OBS runs N concurrent process-loopback captures in one process; prior AEC-lineage work proved concurrent capture in Electron ("Concurrency + process-INCLUDE-captures-Discord-voice proven").
  - **Do the R4 concurrency spike first** (per IMPL-HANDOFF "Parked/deferred"): 2–3 concurrent INCLUDE clients + mixer stable under repeated start/stop in Electron, before committing the design.
- **API is already `pids[]`-shaped** — no ABI break. `tryStartWasapiLoopback` just passes the whole `pids` array instead of `pids[0]`; the widened `AudioConfig.pids: number[]` already carries it end-to-end.
- **Mixer concerns:** per-client drift/resample (each client is event-driven at the fixed format via `AUTOCONVERTPCM`, so alignment should be simple sum-with-small-jitter-buffer), silence/underrun handling per client, and idempotent teardown of N clients (ties into the deferred **WR-02** `stop()` rework — see 999.1-REVIEW.md; do that lifecycle fix as part of this).
- **Verify:** addon CI compile (thomas-quant/wasapi-loopback) → GoofCord win-artifacts → box test that a 2nd device hears ALL checked apps mixed, self-free, no CoreMessaging crash on repeated start/stop.

## Alternative considered (rejected by user)
Constrain the win32 app picker to single-select (radio) to match the shipped single-app backend + Discord's own single-app share model. Small, ships now — but the user wants the real multi-app feature instead.
