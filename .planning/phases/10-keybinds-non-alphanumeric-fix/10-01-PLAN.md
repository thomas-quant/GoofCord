<objective>
Finish the named-key half of KEY-01 (upstream #179). Today `keyCodeToChar` in
`src/windows/main/preload/keybinds.ts` is `OEM_KEYCODE_CHARS[k] ?? String.fromCharCode(k)`,
so control/named keys produce garbage that never matches a venbind token: Enter(13)→"\r",
Space(32)→" ", F12(123)→"{", Page Up(33)→"!". Those binds silently never fire.

This plan (Task A + Task B) makes named keys resolve to venbind's canonical lowercase token
vocabulary and extracts the parsing logic into a pure, bun-testable module guarding the win
with real ground-truth tests. The runtime dependency switch (consuming the fixed venbind
prebuilt `.node`) is a separate, user-gated plan (10-02) — this plan ships verifiable source.

Purpose: Make non-alphanumeric global keybinds register with the correct token, and lock in
regression protection for the already-confirmed punctuation win.
Output: New `keybindShortcut.ts` + `keybindShortcut.test.ts`; `keybinds.ts` refactored to consume them.
</objective>

SPEC CORRECTION (fold into the code comment, do NOT add a numpadenter entry): keep 13→"enter".
The venbind fix emits "numpadenter" for the physical numpad Enter, but Discord's stored shortcut
carries only DOM keyCode 13 with no numpad location, so GoofCord can only ever register "enter".
Net effect: numpad Enter no longer triggers an Enter bind — now CONSISTENT with the Linux backend.
A numpadenter entry would be unreachable from Discord keyCodes; omit it.

Then change `keyCodeToChar` to consult the new table FIRST:
`NAMED_KEYCODE_TOKENS[keyCode] ?? OEM_KEYCODE_CHARS[keyCode] ?? String.fromCharCode(keyCode)`.
Match existing style exactly (tabs, the existing explanatory comment block above OEM_KEYCODE_CHARS;
add a short sibling comment explaining named keys want tokens not chars). Do NOT run `bun run fmt`.
