# Milestone v1.1: Windows Screenshare Echo Fix

**Status:** ✅ SHIPPED 2026-06-06
**Phases:** 3-5
**Total Plans:** 13 (3 + 3 + 7)

## Overview

The Windows screenshare echo fix (upstream #46). On Windows, when a user screenshares system/app audio, Chromium's `"loopback"` mode captured the whole default-endpoint mix — including GoofCord's own playback of the call — so remote viewers heard themselves echoed back. This milestone replaced that whole-mix capture with native WASAPI per-process-tree EXCLUDE loopback (capture everything *except* GoofCord's own Electron process tree), built clean-room from the public Microsoft `ApplicationLoopback` sample (MIT) and shipped as a venbind-style prebuilt `.node` addon.

Native-only scope — the user-side separate-output-device workaround was explicitly NOT a deliverable. The single genuine architectural unknown (getting natively-captured PCM into Discord's web-client `getDisplayMedia` MediaStream in Electron 41.3.0, since GoofCord wraps the *web* client) was de-risked in a distinct GO/NO-GO spike phase before the native investment. All verification was manual on a Windows x64 CI artifact, viewer-side (second device/account) with non-call audio actively playing.

### Phase 4: Native Clean-Room Exclude-Tree Addon + Integration

**Goal**: Build and integrate the actual echo fix — a venbind-style prebuilt `.node` addon (Rust + napi-rs + the `windows` crate) that performs WASAPI process-tree EXCLUDE loopback of GoofCord's own Electron process tree, replacing the whole-mix `"loopback"` capture. Clean-room from the public Microsoft `ApplicationLoopback` sample (MIT — copyright notice retained), never from Discord code. Wired into `screenshare.ts`'s Windows audio branch as an additive 3-way gate (Linux patchcord → Windows native exclude-tree → existing `"loopback"` fallback), delivering PCM via the path proven GO in Phase 3. Exclude target = GoofCord's root Electron PID (via `app.getAppMetrics()`) so the separate Audio Service child is covered. Activation gated dynamically (`LoadLibrary`/`GetProcAddress`) so the `.node` loads everywhere and only *activates* where the API is present (Win10 2004 / 19041+).

## Milestone Summary

**Decimal Phases:** None.

**Key Decisions:**

- Phase shape = spike (3) → native addon + integration (4) → verification + upstream PR (5). The spike gated the native investment.
- Delivery-path spike kept as its own distinct first phase (Phase 3, user's explicit choice) — a GO/NO-GO gate owning no requirement.
- Native-only scope — user-side separate-output-device workaround explicitly rejected as a deliverable (supersedes the research SUMMARY's "workaround-first").
- Build gate relaxed: WASAPI process-loopback is functional on Win10 2004 / build 19041+ (the assumed "20348" minimum was over-stated) — confirmed by official Discord running echo-free on the maintainer's 19045 box; the native path IS locally verifiable, sub-2004 is a minor graceful-fallback (ECHO-03).
- Clean-room boundary LOCKED (D-05): public Microsoft `ApplicationLoopback` sample only (MIT, notice retained), never Discord code/symbols. Hardcode fixed `WAVEFORMATEX`; dynamic LoadLibrary/GetProcAddress load.
- Native ships via the existing prebuilt-`.node` pattern (separate `thomas-quant/wasapi-loopback` repo + one `optionalDependencies` line), mirroring venbind/patchcord.

**Issues Resolved:**

- Echo (#46) eliminated on Windows via WASAPI EXCLUDE-process-tree capture.
- PCM → `getDisplayMedia` MediaStream delivery in Electron 41.3.0 proven (`MediaStreamTrackGenerator` + per-share MessageChannel transport).
- PROPVARIANT Drop freeing the stack activation-params blob (heap corruption) — fixed (afd7e30).
- Dual WASAPI loopback capture (addon + Chromium) crashing system-audio shares — fixed (6e44ebd).
- Native `.node` not unpacked from app.asar at runtime — fixed via `asarUnpack` (ffe49b9).
- Windows-host build portability (native-module glob resolved via fs.readdir, host-agnostic `ts-out/native` copy).
- 2nd-share-no-audio regression (post-PR): WASAPI feeder/transport must be rebuilt per share — fixed (68bfb05).

**Issues Deferred:**

- "Needed a restart once" during testing — characterized as a renderer/Discord-UI hiccup, NOT a native-path failure (all 7 shares across both instances logged `activation=ok`); restart recovered cleanly (matches Core Value).
- WSTRM-01 — further Windows screenshare/streaming bugs beyond cancel/restart + audio → a future milestone.

**Technical Debt Incurred:** None of note. The shipped GoofCord-side diff is surgical (additive `screenshare.ts` gate + `wasapiLoopback.ts` + one `optionalDependencies` line + regenerated IPC); all diagnostic instrumentation stripped.
